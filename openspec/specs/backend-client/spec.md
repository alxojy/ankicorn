# backend-client Specification

## Purpose
The Swift layer over the Rust bridge: generated protobuf types, the generated service and method index, the generic typed call with error mapping, and the typed wrappers for collection and deck methods.

## Requirements

### Requirement: Generated protobuf types
The Swift layer SHALL use message types generated by `protoc-gen-swift` from the `.proto` files of the pinned Anki submodule, never hand-written copies, and the generated files SHALL be committed.

#### Scenario: Regeneration is clean
- **WHEN** `scripts/gen-swift-protos.sh` runs against the pinned submodule
- **THEN** it produces no diff in `app/Cornhub/Backend/Generated/`

### Requirement: Service and method indices
The Swift layer SHALL address engine methods through a generated table of service and method indices that matches the `Backend` dispatch (odd service numbers) of the pinned rslib, and SHALL NOT hard-code numeric literals outside that table.

#### Scenario: Table matches the engine
- **WHEN** the unit tests run
- **THEN** a test calls a method through its table entry for each wrapped method and receives a response that decodes, proving the entry reaches the intended method

#### Scenario: Drift is detected
- **WHEN** rslib's generated dispatch code is regenerated and differs from the committed table
- **THEN** `scripts/gen-service-index.mjs --check` exits non-zero

### Requirement: Generic call and error mapping
`Backend` SHALL expose an async typed call that encodes the request, invokes `run_method`, frees the returned buffer exactly once, and decodes the response. When the engine reports failure it SHALL throw a `BackendError` built from the engine's `BackendError` protobuf, preserving the kind and message.

#### Scenario: Success round trip
- **WHEN** a wrapped method is called with a valid request
- **THEN** the decoded response is returned and the bridge buffer is freed

#### Scenario: Engine error
- **WHEN** `deck_tree` is called before any collection is open
- **THEN** a `BackendError` with the engine's "collection not open" kind is thrown

#### Scenario: Off the main thread
- **WHEN** a wrapper is awaited from the main actor
- **THEN** the engine call runs on a background executor and does not block the main thread

### Requirement: Collection and deck wrappers
`Backend` SHALL provide typed wrappers for `open_collection`, `close_collection`, `add_deck` and `deck_tree`, each named after its engine method, and no scheduling or storage logic.

#### Scenario: Create and read decks
- **WHEN** a collection is opened at a new temporary path and decks "HSK 1" and "HSK 2" are added
- **THEN** `deckTree` returns a tree whose children include "HSK 1" and "HSK 2"
